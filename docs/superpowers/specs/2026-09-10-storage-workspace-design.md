# YouTuber 工作流存储与工作区重构设计

> 日期：2026-09-10 ｜ 状态：待用户审查 ｜ 范围：六个技能 + core + yt-fabu（新建）的交付契约
> 前置决定：交付物全部以**原生 Markdown（.md）**上飞书；四件套 Part 2 宽表**不拆**（用户拍板 2026-09-10）

## 一、背景与问题

现状每个交付物有三个落点（本地持久 md + 飞书 docx + 表格字段），全链路约 17 个写入点，靠文本纪律维持同步；本地按类型分目录与飞书按选题分文件夹语义不一致；`dirs.*` 配置七八项。用户要求：尽可能简洁，人看的放飞书，机器流转的留在本地一次性工作区并机制化清空。

## 二、目标模型（三层）

| 层 | 载体 | 内容 | 生命周期 |
|---|---|---|---|
| **持久层（人读）** | 飞书云盘 `.md` 文件 + 多维表格 | 六个交付物 + 频道词库 + 选题池 | 永不删除 |
| **工作区（机器流转）** | 各技能内 `workspace/` | 活动期中间产物、扫描稿、成品 md | 机制化清空 |
| **索引** | 选题表字段 | 状态机 + 飞书 URL + 人读摘要 | 与池同寿 |

铁律：
1. 交付物恰好两个物理落点：技能工作区（活动期）+ 飞书 .md（持久）。表格字段只存 URL 或人读摘要，**永不存本地路径**。
2. 本地除 `workspace/频道词库.json` 外无任何持久文件；config.yaml 属技能配置不属工作区。
3. 编号是主键：飞书文件夹 `<编号> <标题>/`，工作区 `<编号>/`，文件名固定（见 §3）。

## 四、本地工作区规范

### 4.1 位置与结构

各技能自带，不读 core 路径配置：

```
<技能>/workspace/
├── T-2026-001/          ← 按选题编号一个文件夹
│   └── （该技能的本选题产物，文件名见 §3）
├── T-2026-002/
│   └── …
└── 频道词库.json         ← 仅 yt-guanjianci；根文件，免清
```

### 4.2 清理机制（三档，core 在 progress/route 时顺手执行 + 各技能运行时执行）

| 档 | 触发 | 动作 |
|---|---|---|
| ① 当期自清 | 技能运行开始 | 删除自己 workspace 下**非当前选题编号**的目录（根文件不动） |
| ② TTL 兜底 | core 例行检查 | 目录 mtime 超 TTL（默认 30 天，config 可配）→ 删除 |
| ③ 状态联动 | core 例行检查 | 选题状态 = 已发布 / 已淘汰 → 删除该编号目录 |

清理前输出一行日志（"清理 T-XXXX-XXX 工作区（依据：档② 32 天未动）"）。目录数不设上限（①②③ 在跑时自然压在 2-3 个，无需 max_dirs 伪需求）。

已知取舍：单线推进假设——两选题并行时①档会冲掉另一选题目录；当前工作流为单线，接受。

## 七、边界与例外

1. **并行选题**：①档清理与并行冲突，当前接受单线假设
2. **docx 退路**：若某交付物将来需要飞书评论/协同，单独 `drive +import --type docx` 转真文档，其余保持 .md（混合合法）
3. **fupan 读归档**：低频，`markdown +fetch` 拿回原文；若未来高频批量，再评估
4. **频道词库 JSON**：机器读全部历史，放飞书表格无法结构化消费，故留本地免清
5. **跨技能工作区禁读**：上家推飞书 .md → 下家 `+fetch` 拉回消费（含 keywords.json，经 `05-关键词包.md` 中转）——工作区不跨技能读，无例外

## 八、迁移与验收

1. 迁移（一次性脚本）：`关键词库/`、`分析卡/`、`制作四件套/` 等旧目录内容按编号归入对应技能 `workspace/<编号>/`；频道词库.json 移至 guanjianci workspace 根
2. 验收：脑白金选题全链路实测——每个交付物飞书 .md 可点开、URL 已回填、工作区目录在归档后被清、词库追加正常
3. 回归：各技能扫描闸/机械闸测试全绿（文本层改动零脚本改动原则，仅 §3 无脚本变更）

## 九、不做的事（YAGNI）

- 不做 max_dirs 项目数限制
- 不拆四件套宽表
- 不把频道词库放飞书
